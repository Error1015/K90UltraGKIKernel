## 重做 K90UltraGKIKernel —— 定位并修复"刷进去卡 logo"的真正根因

用户反馈"构建能出包，刷进去起不来"，要求照搬已验证的上游方案重做。

### 根因（终于确定的硬结论）
这台机器的 **boot 分区不是裸内核**，而是整体：
```
[0,4096) boot header v4 (header_size=1584, ramdisk_size=0)
[4096, 4096+kernel_size) 内核 Image
round_up(kernel_size 末尾) → vbmeta blob (2368B, "AVB0")
末尾 64 字节 AVB footer ("AVBf"): original_image_size / vbmeta_offset / vbmeta_size
文件总长 100663296 (96MB 分区大小)
```
换内核后必须把 vbmeta 重定位到新的页对齐位置 + 重写 footer 三个字段 + 保持 96MB。
否则 footer 指向被新内核覆盖的旧偏移 → AVB 校验失败 → 卡 logo、不 panic、不重启。

旧产物两条都踩坑：AK3 只写内核；`boot-k90-custom.img` 只改了 kernel_size（37MB，无 vbmeta 无 footer）。
叠加当时设备还是 LKM 模式（init_boot 里有 kernelsu.ko），双重卡死。

佐证：同机型已验证仓库 wjljh/xiaomi_kernel_for_warsaw_sukisu_susfs 明确写了同一套布局与处理方式。

## 编译期第一挂：susfs.c 未使用 static 函数（commit c1ad682）

现象：配置闸全绿，make 跑到 fs/susfs.o 报

    fs/susfs.c:185:21: error: unused function 'susfs_switch_to_ksu_domain'
    fs/susfs.c:219:13: error: unused function 'susfs_restore_creds'

根因：上游 susfs4ksu(gki-android15-6.6) 的 fs/susfs.c 里这两个 cred 辅助函数
**只在 `#ifdef CONFIG_KSU_SUSFS_PRIORITY_UID_FILTER` 块内**被调用（1643/1714 行）。
BakaSU 的 kernel/Kconfig 只有 10 个 SUSFS 开关，**没有这个符号**（上游代码更新）。
Kconfig 不认识的符号会被 olddefconfig 整个丢掉 → 调用块被编译掉 → 两函数无人用。

修法：project/susfs_66_compat.py 新增 fix_priority_uid_filter_guard()，
把这两个函数（连同紧贴的注释块）用同一个 `#ifdef` 包起来。
验证：去掉新增两行后与上游文件逐字节一致；{} 计数不变；重复执行幂等。

顺带收严配置回读（本来"片段写了、Kconfig 静默丢掉"是无声的）：
- lib.sh 新增 expect_cfg()：符号存在但没生效 → die；符号不存在 → warn 跳过
- build.sh 的 SUSFS 校验从硬编码 2 项改成按 configs/features/susfs.fragment
  逐项回读（9 项 + KSU_SUSFS）

审计结论（下次别再重复查）：susfs.c 里引用但 BakaSU 未定义的符号**只有**
KSU_SUSFS_PRIORITY_UID_FILTER 一个；其余 4 个"仅块内引用"的函数都定义在该块内部，
随块一起被裁掉，不会告警。

## 编译期第二挂：报错行被日志重定向吞掉（commit 468820d）

现象：配置闸全绿（含 9 个 SUSFS + NOMOUNT + BBG + IPSet/CIFS），
make 到 244s 失败，但 "错误摘要：" 后面是空的，只能看到 tail 里的
`AR fs/built-in.a` 和 `make[2]: *** [Makefile:1968: .] Error 2`。

两点判断：
1. `kernel/built-in.a` / `fs/built-in.a` 都归档成功 → SUSFS、NoMount、
   kernel/ 本身没问题，挂的是别的目录（drivers/ net/ security/ 之一）。
2. 旧抓取规则 `grep -E '(^|[[:space:]])(error|Error [0-9]+):'` 只认小写
   "error:"，抓不到 `make[4]: *** [...] Error 1`（Error 后无冒号）、
   GNU as 的 `Error: unknown mnemonic`（大写无编号）、
   `ERROR: Kernel configuration is invalid.`（大写）。
   → 所以摘要为空并不代表错误不存在。

更关键：make 输出被 `> "$OUT/build.log"` 重定向，"编译内核"步骤的
step log 里只有 build.sh 自己的 stdout。产物步骤带
`if-no-files-found: error`，编译一挂 dist 里没东西，日志就没上传 →
彻底丢证据。

### 本次改动
- `--output-sync=target`：每目标输出不交错，根因与 make 摘要行相邻
- `-k`：一次把所有坏点都编出来，避免"修一处 → 重跑 15 分钟"循环
- 失败时三段输出：第一条 `***` 行 + 前 80 行 / 全部 `文件:行:列:` 诊断行 /
  大小写不敏感的疑似错误行
- workflow 新增 `上传构建日志（失败时）`：prepare.log、build-step.log、
  kernel/out/build.log、olddefconfig.log
- build.sh 开头工具链自检（clang/ld.lld/llvm-*/pahole/bc/flex/bison），
  缺工具时直接报名字，而不是 4 分钟后一个 Error 127

## AK3 打包失败：相对路径 + cd（commit bc8657b，已推送）

CI 报 `zip I/O error: No such file or directory`（输出 `dist/ak3-*.zip`）。
原因是 pack_zip 要 `cd` 到临时目录再压，而输出路径是相对仓库根的，cd 之后父目录不存在。
本地没暴露是因为本机没 zip 命令、走 python zipfile 兜底分支（那个分支不 cd）。

教训：**双分支的代码路径必须都被真实执行过**，本地靠兜底分支"通过"会掩盖另一个分支的 bug。
修法：入口统一转绝对路径。回归手段：写 stub `zip` 复刻 CI 的失败判据来跑真实分支。

已推送：158f9cd(ak3) → e8caf88(锁定基准) → bc8657b(路径修复)。
