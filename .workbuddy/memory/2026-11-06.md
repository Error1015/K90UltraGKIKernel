## K90UltraGKIKernel 仓库搭建

目标：为 Redmi K90 Ultra（warsaw / SM8750 / 6.6.57）做 GitHub Actions 构建 GKI 内核的仓库，
支持 KernelSU 系 root + SUSFS 及一系列功能开关。

### 关键调研结论（可复用）
- 小米 `MiCode/Xiaomi_Kernel_OpenSource` 分支 `warsaw-w-oss` 是 Qualcomm kernel_platform 里的
  `msm-kernel` 部分，根目录 Makefile 是 6.6.57；`msm_kernel_la.bzl` 里 `base_kernel = "//common:kernel_aarch64"`，
  说明设备 boot 的内核主体来自 GKI（ACK），小米侧只编 vendor 模块。→ 自建 GKI 是可行路线。
- ACK 没有 `android16-6.6` 分支，Android 16 的 6.6 设备仍走 `android15-6.6`（manifest 分支
  `common-android15-6.6-<yyyy-mm>` / `-lts`）。
- 内核 `scripts/config` 的 `checkarg` 会自动剥离 `CONFIG_` 前缀，带不带前缀都能用；
  `--enable/--module/--disable` 分别写 `=y` / `=m` / `# ... is not set`，字符串用 `--set-str`。
- SUSFS 6.6 补丁（susfs4ksu `gki-android15-6.6`）只含 27 个内核文件的 diff + `fs/susfs.c`、
  `include/linux/susfs*.h`；Kconfig 符号来自 root 管理器（tiann 需额外打 `10_enable_susfs_for_ksu.patch`）。
- 6.6 上 SUSFS 的四个固定坑：base.c 缺 `dma-buf.h`、memory.c 缺 `zswap.h`、`VMA_PAD_START` 宏缺失、
  `show_fdinfo` 3 参 vs `fanotify_fdinfo` 2 参。

- `scripts/{lib,prepare,build,package}.sh` + `scripts/py/{version_pin,susfs_66_compat}.py`
- `config/{base,root/*,features/*}.config`
- 用真实 `scripts/config` 与假补丁做过本地验证：写配置、回读校验、补丁成功/失败路径、compat 幂等性均通过。

## 卡 Logo 定因：LKM 模式残留 init_boot

用户确认：管理器工作模式 = **LKM**；刷入方式 = BakaSU 管理器刷 AK3 zip（正规）；症状 = 卡住不动（非重启）；已用 fastboot 恢复。

调查结论（官方文档 + 机制推导）：
- LKM 模式**不改内核**，改的是 ramdisk；Android 13+ 设备补的是 **init_boot** 分区，塞入 kernelsu.ko 并挂首段 init 的加载钩子。
- 本仓库产物是 GKI 模式（CONFIG_KSU=y），AK3 只替换 boot 里的内核 → init_boot 那份 kernelsu.ko 仍在。
- 那份 .ko 照出厂内核 + 官方 GKI 配置编译；我们改了配置（KSU=y、TRIM_UNUSED_KSYMS=n、SUSFS/NoMount）→ module_layout 等符号 CRC 全变 → insmod 必失败 → 首段 init 等不到模块停住 = 卡住不动。
- 上次"pstore 为空即内核没跑起来"的判断要修正：LKM 冲突下内核其实是活的。

代码改动（commit cceeb0a）：
- README 六.1「头号原因：之前是 LKM 模式，基座没换干净」：原理、分区对照表、正确切换流程（boot + init_boot 都要恢复，或管理器「卸载→恢复原厂镜像」）、状态判断
- README 刷机前自检加第 0 步；六.3 注明 `fastboot boot` 只换 boot、init_boot 仍读 flash，基座不干净会误判成"内核坏了"
- scripts/check-device.sh：adb 只读自检（/proc/modules 判 LKM、grep init_boot 块设备判残留、页大小/KMI/SPL），用假 adb 跑通 LKM/干净两个场景
- package.sh：在 anykernel.sh 注入 ui_print 提示（锚点 `. tools/ak3-core.sh`，幂等）

**结论：不需要重编内核**，现有 Release 包配干净基座应该就能起。

## 一次运行出全部管理器的包（矩阵化）

需求：一个 workflow 任务跑完 bakasu + sukisu + kernelsu(next) 等所有管理器的 AK3；预设默认 full；root 管理器默认全部。

实现（`build.yml` 重写为 resolve → build(matrix) → report 三个 job）：
- 新增 `root_manager=all` 选项并设为默认；`resolve` job 用内嵌 python 把
  **preset × root 解析成矩阵**（`include: ${{ fromJSON(needs.resolve.outputs.matrix) }}`），
  每个组合一个并行 job，各自上传独立 artifact / Release。
- 矩阵净化规则：`preset=vanilla` 时 root 收敛为 `none`（否则 5 个包完全一样）；
  `kowsu` + SUSFS 自动关掉 SUSFS（prepare.sh 里仍是硬失败，但 all 模式不会触发）；
  `root=none` 或 vanilla 时 susfs 强制 false，避免 prepare.sh 的 "SUSFS 需要 root" 报错。
- 矩阵 JSON 结构：`[{"preset","root","susfs"}]`，env 里用 `${{ matrix.susfs }}` 覆盖原 `inputs.susfs`。
- 新增 `report` job：跑完在运行页给总表（每个包对应的管理器 APK）。
- 默认值：`preset: full`、`root_manager: all`（workflow 与 prepare.sh/package.sh 的 `${PRESET:-}` 都改）。

坑/注意：
- YAML `run: |` 块标量会把公共缩进剥掉，heredoc 结束符 `PY` 在 YAML 里缩进 10 空格、落盘后列 0 才合法。
- 矩阵里布尔值经表达式注入 env 会变成 `"true"/"false"` 字符串，`is_true()` 能吃。
- Windows 磁盘上写的 yml 是 CRLF，`.gitattributes` 有 `eol=lf`，提交时会转 LF；本地已手工转 LF 避免 heredoc 带 \r。
- 验证方式：提取每个 step 的 `run` 落盘 `bash -n`，再把 resolve 的 python 用假 GITHUB_OUTPUT 端到端跑一遍。

## Release 发布方式：三态选择

把原来的 `publish_release`（boolean）换成 `release`（choice，默认 `release`）：
- `release` → 正式 Release；`prerelease` → `softprops/action-gh-release` 的 `prerelease: true`；
  `none` → 跳过发布步骤，只留 Artifacts。
- 条件写法：`if: ${{ inputs.release != 'none' && success() }}`；
  `prerelease: ${{ inputs.release == 'prerelease' }}`（表达式渲染成 "true"/"false" 字符串，action 能解析）。
- `make_latest` 保持 `false`：一次运行出多份包，抢 "Latest" 会让最新版本随机落到某个管理器上。
- report job 增加 `RELEASE_MODE` 环境变量，在运行摘要里显示发布方式。
